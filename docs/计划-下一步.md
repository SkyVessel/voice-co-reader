## 任务 ②：主动裁剪（active trimming）—— ✅ 已完成（2026-08-17, commit 574fd1a）

**为什么必须做**：音频 token 12.5 tok/s 且每轮重复计费；模型上限 ~50 轮/300s 音频历史
（40960 tokens 上下文）。不裁剪 = 产品只能聊 10 分钟。这是 pi compaction 的语音版，
决策早已定下（见调研文档"主动裁剪"节），本任务只是落地。

**设计**（在 session.py 实现，provider 无感）：
1. 每轮结束（response.done）记录该轮的 item id 列表（provider 事件里有 item_id，
   需要从 provider 事件透传——目前 _EVENT_MAP 没带 item_id，要加）。
2. 超过阈值（如 20 轮，config 可调）时：
   a. 把最旧轮次的转写文本追加落盘 `notes/session-YYYYMMDD.md`（offload，格式：时间戳+你/AI+文本）
   b. 对旧 item 发 `conversation.item.delete`（Qwen/OpenAI 都支持此事件，item_id 定位）
   c. 可选：发一条 session.update 或注入 system 文本告知模型"早期对话已归档到文件，
      需要时可用 read_file 查阅"（让模型知道有 offload 这回事）
3. 音频本身没有转写稿的轮（早期轮次），至少保留我们已有的 user.transcript_done /
   assistant.transcript_done 文本——session 需要开始累积每轮转写（现在 delta 只是透传打印）。

**验收**：脚本模拟 30 轮对话（文本注入即可），确认 ① delete 事件被接受 ② 模型仍能正常回答
③ 落盘文件有完整转写 ④ token 用量（response.done 的 usage 字段）不再线性膨胀。
顺便把 usage 字段从 response.done 透传到总线（usage 监控是商业化必需的）。
